# Правила работы с репозиторием

## Цель

Подготовить существующую Flappy Bird к публичной презентации в GitHub-профиле:
довести корректность, надёжность, переносимость и оформление до состояния,
которое можно уверенно демонстрировать и поддерживать.

Новые игровые возможности не входят в текущую цель. Сохраняйте существующие
сценарии: меню, настройки внешнего вида, игровой раунд, счёт и перезапуск.
Готовность подтверждается работающей игрой и проверками, а не количеством
абстракций, тестов, badges или документации.

## Область изменений

- Исправляйте ошибки текущего поведения и устраняйте причины регрессий.
- Допустимы обновление зависимостей, обеспечение кроссплатформенности,
  настройка CI, документация и очистка репозитория от генерируемых файлов.
- Рефакторинг должен решать конкретную проблему корректности, сопровождаемости
  или проверки существующей игры. Ограничивайте его затронутыми модулями.
- Новые механики, режимы, экраны, сервисы, сетевые возможности и смена движка
  требуют отдельного запроса пользователя.
- Не превращайте небольшую настольную игру в архитектурный каркас. Используйте
  существующий подход, пока нет конкретной причины его изменить.

## Устройство проекта

- `FlappyBird.sln` — решение; `FlappyBird/FlappyBird.csproj` — приложение.
- `Program.cs` — запуск и параметры окна; `Game.cs` — события и состояния игры.
- `Bird.cs`, `Pipe.cs`, `Score.cs` — поведение птицы, препятствий и счёта.
- `Menu.cs`, `Background.cs`, `TextureDrawing.cs` — меню и отрисовка.
- `GameTextures.cs`, `Textures/` — загрузка изображений и ресурсы.

Текущий стек — C# и .NET 10 LTS (`net10.0`), OpenTK `4.9.4` и
System.Drawing.Common `10.0.14`. Нужен стабильный SDK `10.0.403` или более новый
patch в той же feature band `10.0.4xx`, согласно `global.json`. Нативный запуск
на Linux/macOS пока блокирует System.Drawing.Common; его замена относится к #9.

## Качество и переносимость

- Сохраняйте поведение вне исправляемого дефекта. Изменения управления,
  физики, столкновений и начисления очков объясняйте через конкретный сценарий.
- Отделяйте обновление игрового состояния от рисования, когда это необходимо
  для исправления или тестирования. Скорость игры не должна зависеть от FPS.
- Управляйте временем жизни файлов, изображений, окна и графических ресурсов
  явно, включая пути ошибок.
- Цель — кроссплатформенный запуск; обязательная матрица проверки — Windows,
  Linux и macOS. Проверяйте версии ОС, архитектуры, OpenGL и нативные зависимости.
- Ресурсы должны загружаться независимо от рабочего каталога. Учитывайте
  регистр имён и разделители путей; не используйте персональные абсолютные пути.
- Выбирайте поддерживаемые стабильные версии .NET и совместимые зависимости.
  Совпадение major-номеров само по себе не доказывает совместимость.
- Избегайте Windows-зависимых API в общих путях выполнения. Простое обновление
  System.Drawing.Common не устраняет его платформенные ограничения.
- Применяйте общие инженерные правила Wiki в соответствующей области;
  требования к веб-приложениям не переносите автоматически на C#/OpenTK.

## Проверки

Перед изменением изучите соответствующий issue и затронутые исходники.
Воспроизведите дефект, если это возможно, и выберите проверку его причины.

Команды восстановления и сборки из корня репозитория:

```sh
dotnet restore FlappyBird.sln --locked-mode
dotnet build FlappyBird.sln --configuration Release --no-restore
```

Пока загрузка ресурсов зависит от рабочего каталога, запускайте из каталога
приложения:

```sh
cd FlappyBird
dotnet run --project FlappyBird.csproj --configuration Release
```

После исправления путей ресурсов проверьте запуск из другого каталога и
обновите эту инструкцию. Версию SDK согласуйте с `global.json` и CI.

NuGet-граф зафиксирован в `FlappyBird/packages.lock.json`. При намеренном
изменении зависимостей выполните `dotnet restore FlappyBird.sln --force-evaluate`,
проверьте изменения lock-файла и повторите restore с `--locked-mode`.
Не редактируйте lock-файл вручную. Проверяйте прямые и транзитивные зависимости:

```sh
dotnet list FlappyBird.sln package --outdated --include-transitive
dotnet list FlappyBird.sln package --deprecated --include-transitive
dotnet list FlappyBird.sln package --vulnerable --include-transitive
```

- При создании этого файла тестового проекта и CI workflow нет. Не считайте
  успешное выполнение команды без найденных тестов проверкой поведения.
- Для исправлений добавляйте содержательные регрессионные тесты там, где это
  технически возможно. Вызывайте реальный C# код; не копируйте его логику в тест.
- Проверяйте результат и инварианты: столкновения, счёт, переходы состояний,
  перезапуск, ввод и обработку ошибок. Не тестируйте наличие строк или файлов
  вместо поведения; статические проверки допустимы для статических контрактов.
- Проверяйте сборку на каждой ОС обязательной матрицы. Успешная сборка не
  подтверждает создание окна, отрисовку или работу управления.
- Для затронутых пользовательских сценариев проверяйте реальную игру:
  запуск, меню, настройки, раунд, счёт, завершение раунда, перезапуск и выход.
- Если SDK, графическое окружение или целевая ОС недоступны, укажите это явно.
  Модель на другом языке не заменяет тест production-кода.

## Git, CI и документация

- Одно изменение должно иметь понятную цель и проверяемый результат.
  Не включайте несвязанную уборку в исправление поведения.
- Не коммитьте `bin/`, `obj/`, `.vs/`, пользовательские настройки IDE,
  секреты и временные отчёты. Удаляя артефакты из индекса, сохраняйте рабочие
  файлы пользователя и исходные ресурсы игры.
- Принята схема веток Wiki: `main` — стабильная версия, `stage` — интеграция
  проверяемых изменений. Обычные PR направляйте в `stage`.
- Для обслуживания используйте `chores/<issue>-<description>`, для дефектов до
  выпуска — `bugfixes/B-<issue>-<description>`, для security-работ —
  `security/<issue>-<description>`. База этих веток — актуальный `stage`.
- Production-дефекты исправляйте в `hotfixes/B-<issue>-<description>` от `main`
  с PR в `main`. Новые функции после отдельного согласования идут через
  `features/F-<issue>-<description>` от `stage` с PR в `stage`.
- Перед PR вливайте актуальную целевую ветку обычным merge в чистом рабочем
  каталоге. Прямые изменения в `main`/`stage` и force push запрещены.
- Используйте Conventional Commits. Слияние PR требует независимого одобрения
  и успешных обязательных проверок; после merge удаляйте завершённую рабочую
  ветку. Выпуск `stage` в `main` требует отдельного решения ответственного
  за выпуск и выполняется через PR с merge-коммитом.
- CI должен показывать фактически выполненные проверки и ошибки каждой ОС.
  Не скрывайте сбои ради зелёного статуса и не выдавайте отсутствие тестов за успех.
- README описывает игру, требования и воспроизводимые шаги запуска;
  AGENTS.md — правила работы. Команды и заявленная поддержка должны совпадать
  с проектом и CI. Обновляйте их вместе с соответствующим изменением.
- Не заявляйте права или лицензию на код и изображения без подтверждения.
  Перед публичной презентацией проверьте происхождение и условия использования
  ресурсов, не приписывая им разрешений по умолчанию.

## Отчёт о результате

Укажите, что изменено и зачем, какие команды и сценарии проверены, на каких
ОС, что осталось непроверенным и какие риски сохраняются. Разделяйте факты,
предположения и целевое состояние. Для изменений кода требуется независимое
review перед merge; не называйте всю игру production ready по одной сборке
или зелёному CI.
